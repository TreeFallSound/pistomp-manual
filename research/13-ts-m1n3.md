# TS-M1N3 — Neural TS-9 Model vs gxts9 for the Stacked-Boost Role

This doc extends `03-tube-screamer.md`, which ranked four circuit-model plugins for "a Tube Screamer to stack in front of a fuzz" and picked `gxts9.lv2`. It never considered `TS-M1N3.lv2`, GuitarML's neural TS-9 clone, which ships on the pi-Stomp image. This fills that gap.

### Methodology

Read the full upstream source at the cloned GuitarML/TS-M1N3 repo (HEAD `f1cf48c`, a shallow single-commit checkout):

- `Source/PluginProcessor.cpp` / `.h` — signal flow, model loading, resampling, parameter feed.
- `Source/RTNeuralLSTM.cpp` / `.h` — the RTNeural model definition and per-sample forward pass.
- `CMakeLists.txt`, `installers/linux/build_deb.sh`, `.gitmodules` — how the LV2 is produced and packaged.
- `README.md` — training claims.
- Both `models/model_ts9_cond2.json` and `models/model_ts9_48k_cond2.json` — parsed the actual weight tensors (shapes and `model_data` blocks) with numpy, not the filenames.

Cross-checked against `/Users/cam/dev/pi-gen-pistomp` (image build), `src/_data/plugins.json`, and `src/_data/plugins-source.json`. Verified upstream tags with `git ls-remote`. Where a fact is a claim I could not verify in the source tree, it is marked as such.

All weight shapes, sample rates, and per-sample MAC counts below are measured or derived from the source; the CPU fraction is an order-of-magnitude estimate and is labelled as one.

### 1. Architecture

Measured from `models/model_ts9_48k_cond2.json` `model_data` and tensor shapes:

| Field | 48k model (used) | 44.1k model (dead) |
|---|---|---|
| `unit_type` | LSTM | LSTM |
| `num_layers` | 1 | 1 |
| `hidden_size` | **32** | 20 |
| `input_size` | 3 | 3 |
| `output_size` | 1 | 1 |
| `skip` | 1 | 1 |
| `rec.weight_ih_l0` | (128, 3) | (80, 3) |
| `rec.weight_hh_l0` | (128, 32) | (80, 20) |
| `lin.weight` | (1, 32) | (1, 20) |

It is a single-layer **LSTM**, not WaveNet. The gate tensors have `4·H` rows (128 = 4·32, 80 = 4·20), the standard LSTM packing of the input, forget, cell, and output gates.

The compile-time model in `RTNeuralLSTM.h:28-30` is hardcoded:

```cpp
RTNeural::ModelT<float, 3, 1,
    RTNeural::LSTMLayerT<float, 3, 32>,
    RTNeural::DenseT<float, 32, 1>> model_cond2;
```

so the plugin can only run the **hidden-32** model. See §4 for why the hidden-20 file is unreachable dead weight.

`skip=1` is a residual connection: the network learns the *difference* the pedal adds. `RTNeuralLSTM.cpp:88`:

```cpp
outData[i] = model_cond2.forward(inArray) + inData[i];
```

**Memory / receptive field.** Unlike `gxts9`, which is memoryless in its nonlinearity (a table lookup) with all frequency-dependence in explicit biquads, the LSTM carries a hidden state and a cell state (32 floats each) that persist sample-to-sample. It is effectively an IIR nonlinear system: the receptive field is not fixed but decays with the learned recurrent weights. This is what lets it model reactive, level-dependent transient behaviour — the way a real TS's feedback clipper and coupling caps respond to attack — as learned dynamics rather than as a fixed pre-filter. The cost is that those dynamics are opaque and only characterised at the operating points it was trained on.

### 2. Conditioning — the strong point

`cond2` means two conditioning inputs on top of the audio, giving `input_size=3`. From `PluginProcessor.cpp:187` and `RTNeuralLSTM.cpp:72-88`:

- `inArray[0]` = audio sample
- `inArray[1]` = `driveValue` (the GAIN parameter)
- `inArray[2]` = `toneValue` (the TONE parameter)

Both drive and tone are **genuine trained conditioning axes**, not post-hoc gain. The README states the training set was "five steps for the gain and tone knobs... (0.0, 0.25, 0.50, 0.75, 1.0), for a total of 25 output samples at 2 minutes each" — a 5×5 grid captured off the real pedal, with the model interpolating between grid points via the conditioning inputs at inference. This is the single most important finding for comparing against `gxts9`:

- `gxts9` gets its drive taper from a modelled gain pot (`R2 = 51 kΩ + 500 kΩ·drive`) inside the diode-equation solve — the drive knob is physically in the feedback loop.
- `TS-M1N3` gets its drive by having *trained across the actual knob sweep of a real unit*. This is a fundamentally different and arguably more faithful route to the same thing: the drive response is whatever the physical pedal did at those five positions, not what an idealised model predicts. This is a real point in its favour, and it applies to the tone knob too.

Parameter changes are linearly ramped across the block (`RTNeuralLSTM.cpp:59-86`) to avoid zipper noise.

What is *not* modelled by the net: the MASTER/level knob is a plain post-gain (`PluginProcessor.cpp:199-206`), and there is a fixed `buffer.applyGain(3.0)` input boost (`:175`) that sets the operating level the net expects.

### 3. Training provenance

The README states plainly: "TS-M1N3 is a guitar plugin clone of the **TS-9 Tubescreamer** overdrive pedal." The "M1N3" is a pun ("mine"), **not** a claim of an Ibanez TS Mini — this is presented as a TS-9, the same pedal `gxts9` models. Good: doc 03's subject and this plugin's subject are the same circuit.

**Caveat, stated honestly:** the model JSON files contain only `model_data` (architecture) and `state_dict` (weights). There is **no training metadata** — no capture-unit serial, no date, no rig, no dataset hash. Training was done with Alec Wright's Automated-GuitarAmpModelling (GuitarML fork), per the README, but the actual physical unit that was captured is **unverifiable from the source tree**. We are trusting the README's "TS-9" claim; the weights themselves cannot confirm which pedal produced them. By contrast, `gxts9`'s provenance is fully auditable — it is derived from a named published circuit analysis, and every component value is in the Faust source.

### 4. What the neural model can and cannot capture vs gxts9

**The 720 Hz mid-hump.** If the net was trained on a real TS-9 it necessarily learned the pre-clip high-pass — the mid-hump is baked into every training sample. But it learned it as a property of the trained operating points, not as an inspectable filter. There is no coefficient you can read, and no guarantee the corner stays at 720 Hz across the *continuous* knob range: the model only saw five drive positions and five tone positions, and interpolates between them through the conditioning inputs. `gxts9`'s 720 Hz corner is a computed constant (`R1=4700 Ω`, `C=0.047 µF`) that provably holds at every drive setting. TS-M1N3's mid-hump is present but not provable and not adjustable independently of everything else the net learned.

**Sample-rate dependence — handled by resampling, not by the model.** An LSTM's learned dynamics are tied to the rate it was trained at; its recurrent weights encode a per-sample time constant. The plugin sidesteps this by **always resampling to 48 kHz internally and running the 48 kHz model**, regardless of host rate:

- `PluginProcessor.cpp:114` — `constexpr double targetSampleRate = 48000.0;`
- `:118-121` — it loads `model_ts9_48k_cond2_json` unconditionally.
- `:180` / `:195` — `resampler.processIn` / `processOut` bracket the model, via `chowdsp::ResampledProcess<SRCResampler<>>` (libsamplerate).

Consequences:

| Host JACK rate | Behaviour |
|---|---|
| 48 kHz (pi-Stomp default) | Resampler is ~unity; model runs at native rate. Best case. |
| 44.1 kHz or other | SRC up to 48k and back every block — extra CPU and latency, but the model still sees 48k, so its dynamics stay correct. |

This is actually a sound design: unlike naively running an LSTM at a rate it never saw (which would shift every learned time constant), the code guarantees the net always sees 48 kHz. It resolves the correctness concern at the cost of resampler overhead whenever the Pi's configurable JACK rate is not 48 kHz.

Note the consequence for the two model files: **the 44.1k / hidden-20 model is never loaded.** `prepareToPlay` hardcodes the 48k JSON, `RTNeuralLSTM.h` hardcodes `LSTMLayerT<3,32>`, and `load_json3` even hardcodes the bias loop bound at `for (int i = 0; i < 128; ++i)` (`RTNeuralLSTM.cpp:40`) — that is `4·32`, so feeding it the hidden-20 file (bias length 80) would over-read. There is effectively one model.

**Extrapolation.** A diode equation is valid for any input; `gxts9` cannot be driven out of its modelling domain. An LSTM is only valid inside the input-level distribution it was trained on. TS-M1N3 sets that expected level with the fixed `applyGain(3.0)` pre-boost. Hit it with a signal hotter than the training set saw — a boosted humbucker, or another boost in front — and the output is undefined: it may compress oddly, fold, or lose level, with no physical model underneath to keep it sane. For a pedal you are explicitly stacking *in front of a fuzz*, where levels are hot and unpredictable, this is a real knock.

### 5. CPU cost

Derived from the actual hidden size H=32, input width 3, output 1. Per output sample, per channel:

| Stage | MACs |
|---|---|
| Input weights `W_ih` (4 gates · H · in) | 4·32·3 = 384 |
| Recurrent weights `W_hh` (4 gates · H · H) | 4·32·32 = 4096 |
| Dense output (H · 1) | 32 |
| **Total MAC/sample** | **≈ 4512** |

Plus the gate nonlinearities: per hidden unit, 3 sigmoids + 1 tanh + the cell/output tanh — on the order of 32·5 ≈ 160 transcendental evaluations per sample. On ARM these dominate the real cost; RTNeural uses fast polynomial approximations, but they are still far more expensive than a MAC.

At 48 kHz mono: ≈ 4512·48000 ≈ **2.2·10⁸ MAC/s** plus ≈ 7.7·10⁶ transcendental evals/s. The plugin instantiates **two** independent LSTMs (`LSTM` and `LSTM2`, `PluginProcessor.h:84-85`) and runs one per channel, so a stereo instance doubles this.

Compare `gxts9`: a handful of biquads (a few MACs each) plus one table lookup per sample — order **10¹–10² MAC/sample**, no transcendentals, no per-block resampling. TS-M1N3 is roughly **one to two orders of magnitude** more expensive per sample, before counting the SRC resampler.

**Rough fraction of one Pi core (estimate, not measured):** GuitarML's own NeuralPi deliberately uses hidden-20 to fit comfortably on a Pi in real time; TS-M1N3's used model is the *heavier* hidden-32. A defensible order-of-magnitude figure is **~10–20% of one Cortex-A72 core at 48 kHz mono, roughly double for stereo**, plus resampler cost if JACK is not at 48 kHz. Treat the exact number as unverified — it should be confirmed with `top`/xrun counts on the actual device — but the class is clear: this is a heavyweight plugin, and on a pi-Stomp sharing a core with a fuzz, a delay, and a reverb, it consumes a meaningful slice of the xrun budget that `gxts9` does not.

### 6. Shipped bundle vs upstream

The upstream repo is a JUCE plugin, but it **does** produce an LV2 from the same codebase. `CMakeLists.txt:14-18`:

```cmake
# Build LV2 only on Linux
if(UNIX AND NOT APPLE)
    list(APPEND JUCE_FORMATS LV2)
endif()
```

with `LV2URI https://github.com/GuitarML/TS-M1N3` (matching the `uri` in `plugins.json`). `installers/linux/build_deb.sh:32-33` copies `build/TS-M1N3_artefacts/Release/LV2/TS-M1N3.lv2` into the package. So the shipped LV2 is the JUCE LV2 wrapper around **this exact codebase** — same 48k/hidden-32 model, same internal resample-to-48k, same dead hidden-20 file. Everything in §1–§5 applies to the LV2.

Two things to flag rather than assume:

1. **Version.** `git ls-remote` shows upstream tags top out at **v1.2.0** (and `CMakeLists.txt` says `VERSION 1.2.0`). `plugins.json` records `version: 2.1` for the bundle. That "2.1" is the JUCE-generated LV2 TTL `minorVersion.microVersion`, not the GuitarML release — not a different codebase, just a different version namespace. Worth knowing when reconciling versions.
2. **How it lands on the image is not visible in pi-gen.** `TS-M1N3` does **not** appear in the pi-gen-pistomp install list (`stage2/05-pistomp/02-run.sh`) or the `debpkgs/` tree. The mechanism that places `TS-M1N3.lv2` on the shipped image is therefore **not verifiable from the pi-gen-pistomp source** — it may come from the pi-stomp base package, a MOD plugin pack, or a step I did not locate. I did not confirm that the on-image `.lv2` byte-for-byte matches an upstream JUCE build. If that matters, pull the actual `.lv2` off a device and diff its `model_ts9_48k_cond2.json` against the repo's.

### Impact on doc 03's ranking

**`gxts9.lv2` stays the pick for the stacked-boost role. TS-M1N3 does not displace it.** The role is specific — a low-drive mid-hump boost placed *in front of a fuzz*, running on a Raspberry Pi alongside a fuzz, a delay, and a reverb — and against that role the verdict is not close. Three reasons, in order:

1. **CPU.** In the exact chain this role describes, TS-M1N3's LSTM-32 (per §5, one-to-two orders of magnitude heavier than `gxts9`, more still in stereo or off-48k) eats xrun budget that the biquads-plus-table `gxts9` simply does not. On a shared Pi core this alone decides it, regardless of tone.
2. **The neural advantage is smallest exactly here.** TS-M1N3's real edge is the trained drive/tone axes capturing a physical unit's reactive feel. At *low drive* — the setting for this role — a TS is nearly a clean mid-hump boost with gentle feedback clip. That is the regime `gxts9` renders deterministically and inspectably (provable 720 Hz corner, valid at every knob position). You pay the LSTM's cost for its most nuanced behaviour and then use it in the setting where that nuance matters least.
3. **Level safety.** Stacking into a fuzz means hot, unpredictable input. `gxts9`'s diode equation is valid at any level; TS-M1N3 is only valid inside its training distribution and has no physical fallback outside it (§4).

**The one scenario to reach for TS-M1N3 instead:** use it the way its README intends — as a *standalone, moderate-to-high-drive* Tube Screamer voice into a modelled amp → cab → reverb, when you want the captured feel of a real unit's drive-and-tone interaction and you have the CPU headroom (it is not fighting a fuzz and three time-based effects for the same core). In that use its trained conditioning is a genuine advantage over `gxts9`'s idealised model. For the front-of-fuzz mid-push, keep `gxts9`: Drive ~0.25, Level near unity, Tone ~400 Hz, before the fuzz.
